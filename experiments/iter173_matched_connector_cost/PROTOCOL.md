# Matched-cost connector comparison — frozen before candidate execution

Population A is the 80 executed parent/target requests from the four Iter172
cases, in retained case/call order. REQUESTS.json reconstructs from committed
raw events. Four final attempt-reservation calls had no executed solve; retain
those exclusions explicitly, rather than counting them as controller failures.
This is an exposed conditional request population, not a new tree or a holdout.

Each request preserves parent, sampled target, absolute clock, local horizon,
original per-call transition allocation (at most 1,024), geometry, full point
population and every hard constraint. Both arms run fresh with the same 30-second
per-call cap. This is a new paired replay; Iter172's outer deadline is not silently
reinterpreted as a local cap. Request arms use its unchanged prefix evaluator and
ranking. Root-only returns are missing edges with null distance/route gains;
their binary improvement outcome is false. No fabricated zero gain is assigned.

Population B is the twelve unchanged Iter168 constructive tasks plus left/right
16-step obstacle detours. The new witnesses use zero acceleration and steering
rates following the four-quarter pattern [+1,-1,-1,+1], reflected
for the right case, with four steps per quarter. Targets are generated by scalar
motion. Both sides add a 121-point cluster near forward position 6 m and lateral
position opposite the detour, at 0.5 m height. Straight controls must be rejected
by the background predicate while the complete witness passes. Fixture inspection
before the source freeze verified these conditions without running either candidate.
Both arms receive only explicit tasks and geometry, never witness actions or IDs.
Constructive tasks retain the existing 8,192-transition/30-second envelope, task
phases, terminal tolerances and hard intermediate checks. They assess full paths,
not just prefixes. These cases are disclosed and designed, not holdouts.

Arm shooting imports Iter172's centered solver for requests and Iter171's identical
centered numerical method for explicit tasks. No derivative, residual, scale,
initialization or convergence parameter is changed. Arm forward first evaluates
the same task-derived physical seed. It then enumerates 81 generic combinations:
acceleration and steering amplitudes [0,-1,+1], each with constant, half-reversal
[+,+,-,-], or quarter-reversal [+,-,-,+] signs. Remaining proposals use a fixed
four-phase Halton construction with bases [2,3,5,7,11,13,17,19], mapped to [-1,1].
Phases divide the non-wait portion into quarters. Existing control decoding enforces
explicit wait/stop phases. The family is motivated partly by exposed turn tasks;
that design exposure must accompany any result. It is not OMPL's random constant
control sampler and is not claimed to be a new or optimal planning method.

Both arms use the same full-trajectory evaluator and exact physical-vector cache.
All predicted steps are charged, including motion after a rejection and every
shooting derivative/line-search call. Forward does not terminate a rejected trial
early in this isolation test. This holds evaluation and prefix semantics fixed;
a more efficient early-rejection forward implementation remains untested. Charge
proposal-generation time within the clock, log cache hits and requests separately,
and fail closed if 4,096 proposal requests are exceeded. No hidden rollout or
witness access. Stop immediately on qualified local/global completion as specified
by the common evaluator. Optimizer success does not qualify a task.

Alternate arm order by population index; each arm/request runs in a fresh process.
188 candidate executions, one schedule, no retries or outcome-dependent tuning.
Stage caps: 900 seconds producer and checker each, 1 GiB RSS, 512 MiB output, 2 GiB
free disk before initialization. Per-worker supervisor kills/reaps after 45 seconds
or the remaining stage limit. Use the installed selected-file-bound CPU runtime;
no native RRT, source-scene query, driving episode, provider use or spending.

Primary acceptance requires forward to complete all fourteen constructive tasks,
increase the number of request returns with a target-distance reduction >1e-9,
and not reduce admissible-request count or total checkpoint crossings versus
shooting. No aggregate weighted score or post-outcome tie rule. Report route gain,
paired distance outcomes and attempts separately, alongside prespecified cost
checkpoints 128/256/512/1,024 (clipped to each request's cap). Only fully evaluated
trials within a checkpoint can contribute; carry an earlier return forward after
a legitimate early stop. These are equal available budgets, not a claim of equal
actual work or wall time. A miss contradicts this finite candidate qualification.

Source and runtime freeze before execution; raw commits precede scalar admission.
Check every attempted motion, constraint, prefix selection, control request and
cache identity. Independently reconstruct the forward parameter sequence. Full
scalar masks cover witnesses, straight negative controls and selected returns;
unselected background labels remain producer evidence. The reused local checker
accepts a numeric-input tag named residual; for forward only, normalize that tag
on in-memory copies after checking the real forward_proposal sequence. Raw labels
and optimizer-not-started provenance remain unchanged.

Even a positive result only qualifies a subsequent integrated trial. All four
original integrated cases must separately pass before source comparison. Source
recovery, native driving, transfer, real-time response and competitive superiority
remain unestablished regardless of this comparison's outcome.
