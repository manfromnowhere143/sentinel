# Test whether shorter connections buy useful future expansions

Iter174 admits one of four original completions. Its three misses exhaust the
transition allowance well before the wall-clock cap. Retrospectively, 31/42
selected edges were evaluated by 128 transitions, while eleven needed later work.
Two later edges lie on the completed path. That is a tradeoff to test, not an
online early-stopping oracle. The direct operator authorizes autonomous progress.

Run one prospective 128-cap trial against the retained 1,024-cap result with all
outer budgets and other mechanics fixed. No reference rerun. The independent
checker must reject contract drift and preserve any loss of the existing success.
The all-four acceptance rule remains unchanged. More requests without completions
does not qualify the planner or permit source access.

Pre-execution inspection identifies an interpretation limit: the generator places
Halton proposals after 81 fixed-pattern requests. The shorter cap may never reach
that family. Coverage is therefore a preregistered diagnostic. A result cannot
separate more tree opportunities from changed within-connection proposal coverage.
Do not add another arm or change order after observing the trial.

If qualification fails, stop allocation tuning. Next select a mechanism that
addresses a demonstrated failure, with a constructive control, an adverse control
and a finite falsifier. Alternatives include reachable target guidance, obstacle
guidance, or a distinct controller. The expensive strategic error would be to
turn this project into indefinite planner repair without an actual-history,
deadline-aware information comparison. Keep that mission dependency explicit.

Resources and freeze/admission order are specified in PROTOCOL.md and PLAN.json.
No human ceremony is pending. Passing code tests establishes implementation
checks, not the scientific qualification or state of the art.
